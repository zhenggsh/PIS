# Project InSight（PIS）

PIS 是一个面向小团队的项目计划制定与追踪 Web 应用,基于实用的项目管理经验，提供简单、高效、可扩展的项目管理功能。

## 设计背景

原始需求是「实现项目计划的制定和追踪」，使用Project太繁重，使用Excel无法处理依赖，而且两者都无法实现通过web进行团队协作；
所以，为了指定某个项目的计划，直接使用Trae开发一个Web版本的项目计划制定与追踪工具，实践最有用的项目管理经验；

## 计划管理经验
### 任务分解（WBS分解）
1. 计划总目标分解成N个小目标，无论是大目标还是小目标，必须是可测量的，有明确的完成标准；
2. 目标分解的同级之间，一定是并列的兄弟关系，避免出现男人，女人，老人这样的分解；
3. 要问自己完成了N个小目标是否完整了大目标；同样的，N个小目标进一步分解到多个小小目标
4. 要渐进明细，对两周内的工作，要分解到两三天粒度，两周后的工作可进行粗粒度处理，逐步分解；

### 任务起点终点
1. 起点：一般用个“开工会”作为起点，这个也是依赖的总起点
2. 终点：任务的完成时间，在安排好WBS和依赖后，务必紧盯这个终点

### 任务依赖
1. 逻辑依赖（先设计再研发）
2. 资源依赖（同一个负责人）
经过任务分解、设置起点、终点和依赖，就可以开始安排任务了，计划的静态版本就基本指定了；


### 任务追踪
计划就是用来变的，就是用来更新的，有两种必须的更新
1. 变化带来的更新，因为人员变、需求变、条件变，资源变，等等变化，要及时刷新，并在刷新时考虑对目标带来的变化；
2. 渐进明细带来的更新，因为看不清两周后的工作，原来计划的时间范围大，随着时间的推移，逐渐将任务分解到更细粒度，更准确的时间点；

计划变更的原则
1. 计划就是用来更新的，计划更新的过程就是保证任务终点完成的过程；
2. 最终目标是不能改变的，改变最终目标已经超出项目经理的职责范围；若不得不改变目标，必须向上沟通并得到批准；
3. 某项任务不能到最后一天才发现，因某种原因不能完成，必须提前识别，否则谁也没有办法完成这个任务；
4. 更不能存在过去时间点的任务；经常有项目经理投诉，你看这是上个月要完成的，现在还没有做完。（这个逻辑是不成立的）
5. 在追踪过程中，只能调整时长和依赖关系，不能手工调整开始时间和终止时间. 如果发现影响总进度和关键里程碑，就要采取措施

赶工万能6条措施
1. 延迟工作时长，延迟每天和周末的时间
2. 任务并行，多项任务同时行，切开关键路径任务
3. 减范围，时间不能变，质量不能变，能变的只有范围
4. 用好资源和设备；
5. 用专家力量；
6. 好方法提高质量（减少返工）

在Porject软件中使用原则：
1. 只有起点可以手动设置开始时间，一般是个启动会之类的；
2. 全部都是自动任务；
3. 不要手工调整开始时间和结束时间，只能调时长和依赖；


设计文档把它拆成五条可实现的能力：

1. 多层级工作分解：增删改、缩进与排序、WBS 编码、父节点日期汇总。
2. 项目开工会作为无前置任务的默认起点。
3. 用工作日工期、资源与前置依赖安排工作，起止时间由排期引擎推算，而不是手填。
4. 项目初验点，并形成甘特图。
5. 过程中调整工期或依赖后自动重算，并指出是否影响初验。

## 主要功能

当前可运行的页面只有两条路由：`/` 项目列表，`/projects/[projectId]` 项目工作区。工作区有三个页签：甘特图、任务表、项目设置。

**项目。** 列表可新建、删除项目。新建时填写名称、可选代号（缺省自动生成 `PIS-` 前缀）、描述、开工会、初验点、工作周掩码和叶子工期上限（默认 3 个工作日）。初验点早于开工会会被拒绝。创建后自动写入两个零工期里程碑：「项目开工会」（`isKickoff`，WBS `1`）和「项目初验点」（`isPreAccept`，WBS `2`），并立刻跑一次排期。这两个锚点任务不能删除，日期在项目设置里改。项目状态取值为规划中、执行中、暂停、已关闭。

**工作分解与任务字段。** 
任务类型为汇总（SUMMARY）、工作项（TASK）、里程碑（MILESTONE）。
任务表支持行内改名称、时长、资源（自由文本）、前级依赖和进度；
可上移、下移、缩进、升级、在下方插入同级任务。
缩进时若上一兄弟不是汇总节点，会把它提升为 SUMMARY，并把原来挂在它身上的依赖边转接到新子任务，避免后续任务突然失去前级。
WBS 编码在结构变化后按显示顺序重算。
插入同级任务时，若未手选前级，会默认继承显示顺序中最近的一个可参与依赖图的任务（开工会除外的初验点不作为自动前级）。



**依赖与校验。** 
依赖类型只创建 FS
依赖不能成环
必须有动开始到终点的路径

保存前在同一事务里跑 `validatePlan`：

| 规则 | 级别 | 当前行为 |
| --- | --- | --- |
| V1 除开工会、初验点锚点和汇总节点外，必须有前级依赖 | 阻断 | 拒绝保存 |
| V2 循环依赖 | 阻断 | 拒绝保存，并返回环路任务 |
| V3 叶子工作项工期超过项目 `maxLeafDays` | 建议 | 确认后可保存；一周内（≤5 天）与更长工期文案不同 |
| V4 已开工或已有实际开始日的任务，补丁里直接出现计划起止日期 | 建议 | 确认后以 MSO 落地 |



**甘特图与导出。** 
甘特图为自研渲染：左侧 WBS 列，右侧按日时间轴，周末与节假日用底色区分；
条形表示任务（关键路径、已完成用不同颜色，条内按进度填充），菱形表示里程碑，SVG 折线表示依赖，虚线标出开工会、初验点和今日。

**尚未做成功能的界面。** 顶栏「资源」「审计」「用户」没有链接。用户区写死为 `zhenggsh` /「SSO 已登录」，退出、个人设置按钮没有处理函数。没有登录页、成员邀请或角色鉴权。

## 主要系统架构和实现

```
浏览器
  ProjectList / Workspace（甘特图、任务表、设置、对话框）
        │  Server Actions（"use server"）
Next.js 服务端
  server/actions/*   入参检查与 revalidatePath
  server/plan.ts     事务：变更 → 校验 → 重算 → 回写派生字段 → 审计
  server/workspace.ts  读库后再算一遍排期，组装视图（不落库）
  lib/scheduler/*    日历、拓扑、正逆推、汇总展开、冲击报告（纯函数）
  lib/validation/*   V1–V4（纯函数）
        │  Prisma 7 + better-sqlite3
SQLite（DATABASE_URL，缺省 file:./dev.db）
```

技术栈以 `package.json` 为准：Next.js 16.4.4、React 19.3、TypeScript、Tailwind CSS 4、Prisma 7.10 与 `@prisma/adapter-better-sqlite3`、Vitest 4。`zod` 在依赖中，`src/` 下没有引用；入参检查写在各个 Action 里（空名称、日期格式、初验不早于开工会、枚举取值等）。`next.config.ts` 把 `better-sqlite3` 标为服务端外部包。

**写路径。** `applyPlanChange` 在一条事务里：读变更前计划、执行 `mutate`、用同一份 `validatePlan` 复算、阻断项或未确认的建议项抛 `PlanValidationFailure` 并回滚、否则 `computeSchedule` 并把 `plannedStart` / `plannedEnd` / `isCritical` / `totalFloatDays` / `scheduleSource` 写回任务，最后插入 `AuditLog`。页面使用 `dynamic = "force-dynamic"`，写成功后 `revalidatePath`。客户端不在浏览器里跑排期引擎，编辑都要等服务端往返；打开工作区时 `loadWorkspace` 会再算一次用于展示，因此图上的日期以当次计算结果为准。

**排期引擎。** `lib/scheduler` 零 IO。`calendar.ts` 用位掩码和节假日集合做工作日判断、顺延和工作日加减（工期含首日：1 天则起止为同一天）。`topo.ts` 做 Kahn 拓扑并返回环。`dependency-expand.ts` 把「依赖汇总节点」展开成叶子边。`impact.ts` 对比变更前后快照，给出余量差、日期变化和新旧关键任务。`index.test.ts` 覆盖单链 FS、滞后、菱形会合、节假日、MSO 吸附、环、余量为正/零/负、初验点锚定与被前级驱动、汇总 roll-up、依赖汇总节点。

**校验。** `lib/validation` 同样是纯函数，`index.test.ts` 覆盖 V1–V4 的主要正反例。服务端是权威校验；任务表在选前级时会在前端排除会形成自环的候选（自身与后代），环的最终判定仍在服务端。

**数据模型（`prisma/schema.prisma`）。** 已建表：`User`、`ProjectMember`、`Project`、`Holiday`、`Task`、`Dependency`、`AuditLog`。注释写明 v1 未启用登录，用户与成员只是预留结构，业务代码没有创建用户或检查角色。资源是 `Task.assignee` 字符串，没有 `TaskAssignee`。没有基线表，没有扫描报告表。`Task.version` 有字段，更新语句没有按 version 做条件写入。`AuditLog` 没有操作者外键，影响信息放在 `payload` JSON 字符串里。Prisma Client 生成到 `src/generated/prisma`（已 gitignore）。仓库没有 `prisma/migrations`，脚本是 `db:push` / `db:studio`。

**目录与测试。** 页面在 `src/app`，工作区组件在 `src/components/workspace`，项目列表在 `src/components/project`。测试只有上述两组 Vitest 单测，没有 Server Action、WBS 重编号或界面测试。近期提交为脚手架初始化加上当前这一版计划功能（`init`），没有更细的功能分批记录。

## 下一步开发建议

下列事项都对应代码或设计文档里已经露出、但尚未接上的缺口。

1. **补上真实身份与权限。** 顶栏用户、退出和个人设置是静态界面；「资源 / 审计 / 用户」不可点击。`User`、`ProjectMember` 和 `Role`（OWNER / PM / MEMBER / VIEWER）已建模却未被 Action 使用。写操作目前任何人打开页面即可执行。应先接登录，再在 `runChange` 入口按项目角色拒绝越权，并让顶栏导航指向真实页面。

2. **把已经写入的审计展示出来。** `applyPlanChange` 会记 action、目标、已确认的规则编号和冲击摘要，但没有读取界面。审计页至少应按项目、时间倒序展示这些 payload，否则「确认后记入审计」在产品上不可见。

3. **补齐并发控制。** `Task.version` 已存在，更新没有 `where: { id, version }`，也没有冲突后的刷新提示。多人同时改同一项目时，后写会覆盖先写。设计文档里的乐观锁可以直接落在 `applyPlanChange` 上。

4. **让汇总进度与引擎结果一致。** `computeSchedule` 会按子节点工期加权算出汇总 `progressPct`，`persistSchedule` 不写该字段，`loadWorkspace` 展示的是库里的 `task.progressPct`。父节点进度因此不会随子节点填报更新。要么回写派生进度，要么在视图层改用本次排期结果。

5. **用上已声明但未调用的 zod。** 依赖已安装，Action 仍是手写判断，和设计文档「字段格式交给 zod、业务规则交给 validatePlan」不一致。把 `CreateProjectInput`、`UpdateTaskInput` 等收成共享 schema，可避免前后端各写一套范围检查。

6. **扩大测试面。** 排期与 V1–V4 有单测，事务回滚、WBS 重编号、缩进时的依赖转接、自动前级、初验点锚点不可删，都没有测试。这些分支集中在 `server/plan.ts` 与 `server/actions/task.ts`，适合先补集成测试，再考虑浏览器级流程（建项目 → 插任务 → 改工期 → 看到初验余量变化）。

7. **甘特图与本地预览。** 图是只读时间轴加点击编辑，没有拖拽改依赖、没有长列表虚拟化。引擎已经是纯函数，但每次编辑都等 Server Action。可在提交前用同一份 `computeSchedule` / `validatePlan` 做本地预览，减少「处理中」往返；虚拟化留到单项目任务量上来之后再做。

8. **按设计文档补尚未编码的能力，并改 README。** 仍缺：基线快照与对比、计划发布前的全图复检、V5/V6 扫描（`aiScanEnabled` 默认关闭）、SS/FF/SF、把自由文本资源换成成员分配、PNG/Excel 导出。生产库仍是 SQLite，且没有 migration 目录。`README.md` 仍是脚手架说明，应写明 `DATABASE_URL`、`npm run db:push` 和当前已实现范围，避免把设计文档中的认证、基线和外部模型当成已经可用。
